⚙️ scrumia-gradle

Gradle l'outil, énoncé dans ses termes — format du script de build, catalogue de versions, forme du plugin de convention.

slot · aucun version · 0.1.0

Ce dont il est responsable

Huit règles qui façonnent un projet Gradle pour que l'outil reste rapide et le script de build reste lisible. Les scripts de build sont .gradle.kts, jamais .gradle ; chaque version de plugin et de bibliothèque vit dans gradle/libs.versions.toml ; la logique de build partagée vit dans un composite build-logic comme plugin script précompilé ; les tâches utilisent tasks.register pour l'évaluation paresseuse ; les caches de build et de configuration sont actifs par défaut ; un sibling construit localement se câble via includeBuild(...) ; les versions de plugins vivent dans le bloc pluginManagement ; les tâches de documentation se branchent sur check ou build. Livre une compétence de référence scrumia-gradle et une compétence scrumia-gradle-audit qui mesure un projet existant contre les huit.

Ce qu'il refuse

Un fichier Groovy .gradle dans un projet dont ce module est responsable. Un littéral de version dans un script de build. Un bloc plugins { id("...") version "..." } hors de pluginManagement. Un tasks.create sans commentaire qui en nomme la raison. Un snapshot Maven d'un sibling que l'équipe édite aussi. Un plugin de convention en forme Kotlin Multiplatform dans la prose de ce module — cette forme appartient à scrumia-kotlin-multiplatform-mobile, cité ici seulement comme l'endroit où la forme s'applique.

L'hypothèse qu'il fait

Présume que Gradle est un outil de build, pas un outil spécifique à Kotlin Multiplatform, et énonce chaque règle dans les termes de l'outil. Un projet purement JVM (Spring, Android, une CLI) reçoit les mêmes règles qu'un projet Kotlin Multiplatform Mobile — le satellite se couche par-dessus celui-ci plutôt que de le remplacer. Coûte la friction d'un catalogue de versions sur un projet à un seul module, le rend en un endroit unique qui dit ce que le projet fait tourner.
