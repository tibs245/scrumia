🟣 scrumia-kotlin

Le langage sur lequel l'équipe s'est accordée, écrit noir sur blanc.

slot · aucun version · 0.1.0

Ce dont il est responsable

Six familles de règles de refus qui marquent l'endroit où la sémantique documentée de Kotlin s'arrête et où le mauvais défaut commence : val par défaut, var seulement quand la réassignation est le comportement ; ? sur toute valeur qui peut être absente, et !! seulement avec une preuve locale énoncée ; la concurrence structurée et l'annulation coopérative plutôt que GlobalScope.launch ; data class, hiérarchies sealed et value class choisis selon la forme ; fonctions top-level et objets nommés plutôt que companion object sans état ; et visibilité réglée à la granularité que la surface est censée traverser. Livre une compétence scrumia-kotlin-audit qui mesure une base de code Kotlin existante contre les six, chaque constat citant la règle qu'il enfreint.

Ce qu'il refuse

Un var avec une seule affectation. Un !! sans preuve sur la ligne au-dessus. Un GlobalScope.launch hors bootstrap. Un runCatching autour d'une suspension qui avale CancellationException. Un equals / hashCode / toString écrit à la main là où un data class l'aurait généré. Un companion object dont chaque membre est sans état. Un champ public promu pour faire taire un test qui a traversé la mauvaise frontière.

L'hypothèse qu'il fait

Présume que la documentation du langage Kotlin est la citation de chaque règle — pas d'article de blog, pas de tutoriel, pas de pattern communautaire. Coûte de la discipline sur chaque var, chaque !!, chaque launch, et chaque modificateur de visibilité, et le rend en code qui se lit comme le langage le documente. Le module est compose-only : pas de bin/, pas de dependencies.jsonl ; il contribue à la composition par extends.json et rien d'autre. Un projet purement JVM (Spring, Android) active scrumia-kotlin seul et obtient les mêmes règles ; scrumia-functional-programming, scrumia-kotlin-multiplatform-mobile et scrumia-gradle ne sont pas présumés.
