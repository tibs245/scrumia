# Versions live in the catalog

> Every plugin and library version is declared in `gradle/libs.versions.toml`. A version literal in a build script is a finding.

## Prerequisites

[01-build-script-format](01-build-script-format.md) — the build script is `.kts`, and
its dependencies read from the catalog.

## Rules

### Rule 1: `gradle/libs.versions.toml` is the one place versions live

Every plugin and library version is declared in the version catalog. The catalog is a
single file at `gradle/libs.versions.toml` (the default path) and is structured under
three tables: `[versions]`, `[libraries]`, `[plugins]`.

```toml
# gradle/libs.versions.toml — the only file that holds a version
[versions]
kotlin = "2.1.20"
junit = "5.12.2"

[libraries]
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }

[plugins]
kotlin-jvm = { id = "org.jetbrains.kotlin.jvm", version.ref = "kotlin" }
```

A version literal in `build.gradle.kts` — `"2.1.20"` in a `dependencies { … }` block,
`version "1.0.0"` in a `plugins { … }` block — is a finding the audit names.

### Rule 2: Build scripts read the catalog, never redeclare

```kotlin
// build.gradle.kts — reads the catalog
plugins {
    alias(libs.plugins.kotlin.jvm)
}
dependencies {
    implementation(libs.junit.jupiter)
}
```

The `libs` accessor is generated by Gradle from the catalog and is the only entry a
build script uses. A `dependencies { implementation("org.junit.jupiter:junit-jupiter:5.12.2") }`
form is the literal-version finding; a `plugins { id("...") version "..." }` form is the
pluginManagement finding that [07-plugin-management](07-plugin-management.md) governs.

### Rule 3: A new dependency goes to the catalog first

Adding a library or a plugin is a two-step change:

1. Add the entry to `gradle/libs.versions.toml` under the right table.
2. Read it from `libs.<accessor>` in the build script.

A commit that adds the entry to the build script without the catalog entry is the
finding; a commit that adds the catalog entry and reads it is the conformance.

## Why

A version catalog is one file that says what versions the project runs, and one file
that a reviewer reads when a CVE lands or an upgrade is planned. Without it, every
build script in the project carries its own copy of the version and the project's
"what are we running" question is answered by grepping build scripts. The catalog is
what makes the question answerable in one place, and what makes a Gradle upgrade a
catalog edit instead of a build-script search-and-replace.
