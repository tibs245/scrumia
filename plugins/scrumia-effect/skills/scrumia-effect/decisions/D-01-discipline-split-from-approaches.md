# D-01: The discipline is split from the four approaches, not absorbed into them

**Status**: Adopted
**Date**: 2026-08-22
**Impacts**: [guides/01-typed-effects.md](../guides/01-typed-effects.md), [guides/02-describe-before-execute.md](../guides/02-describe-before-execute.md), [guides/03-effect-boundary.md](../guides/03-effect-boundary.md), [guides/04-service-locator-avoided.md](../guides/04-service-locator-avoided.md), [guides/05-result.md](../guides/05-result.md), [guides/06-either.md](../guides/06-either.md), [guides/07-io-suspend.md](../guides/07-io-suspend.md), [guides/08-effect-website.md](../guides/08-effect-website.md), [guides/09-when-to-throw.md](../guides/09-when-to-throw.md), [guides/10-retry-as-data.md](../guides/10-retry-as-data.md)

## Context

The four canonical approaches to typed effects (`Result`, `Either`, `IO`/suspend, effect.website) cover a wide surface — and the discipline that underlies them (typed effects, describe-before-execute, the effect boundary, service-locator avoided) is the same across all four. The decision this module has to make is whether the discipline lives **inside** each approach section, repeated four times, or **alongside** them, layered beneath them. The repeated form has the cost that every change to the discipline has to be made in four places; the layered form has the cost that the approach sections have to refer to the discipline, and a reader who lands on an approach section must read the discipline first to apply it.

A second question is whether to ship the discipline **at all** when the project only uses one approach. A `Result`-only project does not need to know what an `Either` is, and a rule about `Either`'s left-for-failure convention is not load-bearing for it. The discipline, by contrast, applies regardless of which approach the project uses — the typed-effect rule is the same whether the description is `Result`, `Either`, `IO`, or `Effect<R, E, A>`.

## Arguments For (split, with the discipline layered beneath the approaches)

- **The discipline is the same across all four approaches; absorbing it into each would duplicate the rule four times and invite drift.** The typed-effect rule, the describe-before-execute rule, the effect-boundary rule, and the service-locator-avoided rule do not change between `Result` and effect.website — they apply because of what the approach is, not which one it is. Repeating the same rule four times is what makes it drift: a reviewer finds a `Result` version that says "throw on programmer error" and an `Either` version that says "return a typed error," and decides which one to keep, when the discipline says "name it in the signature."
- **A `Result`-only project reads no `Either`-specific rule as load-bearing, because the approaches are layered, not parallel.** The `Result` guide is a self-contained entry; the `Either` guide is a separate entry; the discipline is the layer both sit on. A reader landing on `Result` reads the discipline (for the rules that apply regardless) and the `Result` section (for the rules that apply only to `Result`); they do not read `Either` and do not read effect.website.
- **The four approaches' separation matches what the four approaches actually are.** `Result` is a value-type pair; `Either` is a two-channel sum type with a polarity convention; `IO`/suspend is a description/execution split with a runtime that runs the description; effect.website is the reference implementation with environments and layers. Conflating any two loses what each one is for. The discipline says what they all have to satisfy; the approach sections say what each one is.
- **A new approach (Arrow's `Raise`, Kotlin's `Result.runCatching`, Scala 3's `Either` extensions) can be added later by writing one approach section and pointing it at the discipline.** The discipline does not have to be re-stated for the new approach; it is the layer the new approach sits on top of. This is the property the four-approach taxonomy buys: extensibility without rewriting.

## Arguments Against (absorb, or skip the discipline)

- **The layered form has a reading cost: a reader who lands on an approach section must read the discipline first to apply it.** A reviewer finding an `IO` that runs at construction must read the describe-before-execute rule to know why that is a finding. The cost is real; the mitigation is the SKILL.md routing table, which lists the discipline guides first and labels them "required" relative to the approach guides.
- **The layered form has a maintenance cost: every change to the discipline has to be evaluated against each approach.** A change to the typed-effect rule has to be checked against `Result`, `Either`, `IO`, and effect.website to see whether it still applies. The mitigation is the same as for the first cost: the discipline is what each approach is layered on, and a change to it should make sense for all four. A change that does not is a signal that the rule is actually approach-specific and belongs in the approach section, not the discipline.
- **"A `Result`-only project reads no `Either` rule" could be read as "the discipline alone is enough for a `Result`-only project, and the module is over-scoped."** The argument is right about the reading: a `Result`-only project reads the discipline + the `Result` section + the error-semantics sections, and the `Either`, `IO`/suspend, and effect.website sections are not consulted. The argument is wrong about the over-scoping: the module ships all four because a project that adopts `Either` later (or runs both `Result` and `Either` for different layers) reads the additional section, and shipping the discipline + the four approaches is what lets the project change approaches without changing modules.

## Verdict

**Adopted.** The discipline lives in its own section (01-04), the four approaches live in theirs (05-08), and the error semantics section (09-10) applies regardless. A reader landing on the module reads the discipline first; a reader landing on a specific approach reads the discipline + that approach + the error semantics. Every guide's first line names the approach — `Result`, `Either`, `IO`/suspend, effect.website, or discipline-level — so a reader can tell in one line whether the rule applies to what they use.

The discipline is the layer the four approaches sit on top of, not a substitute for them, and the SKILL.md routing table makes the layering explicit. A change to a discipline rule that does not apply to one of the approaches belongs in that approach's section, not the discipline, and the approach guide that disagrees with the discipline is a finding against the approach guide.
