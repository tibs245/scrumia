# cocoapods-swift-interop

*Norm.* Cocoapods integration is declared once, per pod, with the iOS deployment target and the Swift bridging configuration — no pod reaches the build twice, no Swift consumer wires twice.

## What is required

A Kotlin Multiplatform module that depends on a Cocoapods pod declares the pod once, by name, with the deployment target every consumer of the module compiles against. The Swift bridging is configured by the iOS application that imports the module, not by the module itself: the module's responsibility is the interop, the application's responsibility is how it reaches the module's API from Swift.

```kotlin
// build.gradle.kts
plugins {
    kotlin("multiplatform") version "2.0.0"
    kotlin("native.cocoapods") version "2.0.0"
}

kotlin {
    iosArm64()
    iosSimulatorArm64()

    cocoapods {
        ios.deploymentTarget = "14.0"

        pod("Alamofire") {
            version = "~> 5.8"
            extraOpts += listOf("-compiler-option", "-fmodules")
        }
    }
}

name = "shared"
```

The `kotlin("native.cocoapods")` plugin generates a Podspec the iOS application can pull in. The pod's Swift bridging header is generated by the same plugin from the pod's `.modulemap`. A pod declared once here is the pod the iOS application sees, with no second declaration in the iOS project's own `Podfile` that would shadow it.

## Why

The Kotlin documentation states:

> "You can use CocoaPods dependency managers in your multiplatform project to add iOS-specific dependencies. To set up a project with CocoaPods, declare the `kotlin("native.cocoapods")` plugin and configure dependencies."

A pod declared twice — once in the KMP module and once in the iOS project's `Podfile` — is two pods the linker has to resolve, with the second one overriding the first whenever the versions disagree. A bridging header configured by the iOS application when the KMP module has already declared it is two headers for the same module, and a Swift consumer that imports one has to choose.

The iOS deployment target is what the KMP module's generated Podspec advertises. Setting it on the KMP side means the iOS application's deployment target is the one the build verified against; setting it on the iOS side means the KMP module's pods have to wait for the iOS project's `Podfile` to land, and a build that runs only the KMP module has no deployment target to verify.

## What is refused

- A pod declared both in the KMP module and in the iOS project's `Podfile` — two declarations of the same dependency, one of which is a shadow.
- A bridging header configured in the iOS application for a module the KMP side already configured — two headers for the same module.
- An iOS deployment target set only in the iOS project's `Podfile` when the KMP module pulls in pods — the KMP module has no target to compile against, and a build that runs only the KMP module has nothing to verify.
- `kotlin("native.cocoapods")` applied to a module that does not depend on a pod — a configuration the build accepts without anything for it to bridge.
