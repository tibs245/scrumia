01 — the run

One run, end to end.

The reference composition, executing. Blue is where the run stops and a person decides — it happens three times, and never by accident.

  1. 01human

    Brief

    An idea, a problem. Nothing formatted, nothing estimated — the vague version, out loud.

    uses — no module —

  2. 02agents

    Scoping

    The brief is challenged until it can be split into features. A vague brief has nothing to converge on, and this is where that shows.

    → issues + specs branch uses discovery

  3. 03agents

    Refinement

    Standing roles weigh in from their own scope, and the ticket splits into sub-issues, one per context.

    → Ready for dev uses tracker + team

  4. 04human

    Sign-off

    Only where doubt, criticality or risk warrant it. The run waits; it does not guess your answer.

    uses — no module —

  5. 05agents

    Sprint

    The manager batches tickets that will not collide, and sizes the model each one runs on.

    → To dev uses team

  6. 06agents

    Build

    One worktree per ticket. Spec, code, tests, review — each agent summoned for its one job and resolved when it is done.

    → PRs uses team + implementation + practices

  7. 07human

    Merge

    Review the PR, test it, take the call. The final one stays yours, unless you explicitly delegate it.

    → Done uses — no module —

02 — the argument

An empty slot is not a missing feature. It is a capability the project does not have — and the agents are told so.

This repo runs with three slots empty. Here is what its agents read, in the file the composition writes:

The discovery slot is empty: scrumia-discovery is not installed. An idea therefore goes straight to a ticket without a scoping pass — say so rather than improvising one.

Nothing gets faked. That is the whole difference between a composition and a checklist.

03 — slots

Seven questions. One module each.

A slot is a question your project has to answer. A module is one answer to it. The board below is this repo's actual composition — try filling the hole.

board state 4 filled · 3 deliberately empty

specs

Where do specs live, in what shape?

One directory per feature, files created only when they have content, acceptance criteria written first and turned into tests.

✓ scrumia-specs

tracker

Where does state live — tickets, columns, PRs?

GitHub Issues and Projects. Nothing stateful in the repo; a hook enforces it.

✓ scrumia-github-project

team

Which standing roles, with what scope?

Manager, business, tech. Each boundary is a line of refusal. Roles toggle by config.

✓ scrumia-teams

design

Where does the design system live?

Identity, tokens and components as files in the repo. A value the tokens don't carry is a finding, not an exception.

✓ scrumia-design

discovery

How does an idea become scoped work?

Empty here, on purpose. Agents send an idea straight to a ticket, and say that no scoping pass exists.

nothing installed

implementation

How is code written, per app?

Empty here — this repo ships markdown, not code. Elsewhere: one module per stack, Rust or SolidJS.

nothing installed

practices

Which cross-cutting practices, per app?

Empty here. Elsewhere: TDD, SOLID, TanStack Query — each with reference, audit and refactor skills.

04 — modules

Twelve shipped.

Each one is a standard Claude Code plugin. Install what you need, ignore the rest, and write your own when none of them answers your question.

  • scrumia-core

    kernel2 skills

    Describes the active composition and writes it into CLAUDE.md. Fills no slot.

  • scrumia-rules

    no slot4 skills

    Rule sections a project can own: index, guides, decisions — no rule without its why.

  • scrumia-specs

    specs3 skills

    Per-feature specs, TDD-oriented. A file catalog instead of one document.

  • scrumia-github-project

    tracker5 skills · 1 hook

    Issues, sub-issues, Projects columns, branches and PRs. Requires gh.

  • scrumia-teams

    team3 agents · 2 skills

    Standing roles and sprint execution in dynamic workflows. Roles are configurable.

  • scrumia-discovery

    discovery2 skills

    Challenges an idea until it can be split, then ships specs on a branch.

  • scrumia-impl-rust

    implementation2 skills

    Invalid states unrepresentable, typed errors per layer, one test per invariant — plus an audit skill for existing code.

  • scrumia-impl-solidjs

    implementation2 skills

    Fine-grained reactivity without React reflexes, behaviour-first component tests — plus an audit skill.

  • scrumia-practice-tdd

    practices3 skills

    The cycle operationalized for an agent, the mock boundary, AC-to-test mapping. Reference, audit, refactor.

  • scrumia-practice-solid

    practices3 skills

    The five principles, each with its limit. Audits violations and over-applications alike.

  • scrumia-practice-tanstack-query

    practices1 skill

    Query keys, options, mutations, testing — 9 guides, 13 decisions, ported from real monorepo use.

  • scrumia-design

    design1 agent

    Identity, tokens and components in the repo, synced one at a time. Ships the designer role and an audit that reports drift and mutedness alike.

05 — install

Two commands, then a question.

# add the marketplace, install the kernel
/plugin marketplace add tibs245/scrumia
/plugin install scrumia-core@scrumia

# then, in the repo to set up
/scrumia-core:scrumia-init

scrumia-init maps your apps, proposes a composition, offers the install command for each module it needs, and writes the result into CLAUDE.md. Re-running it checks instead of overwriting.

Prerequisites: git, an authenticated gh CLI for the GitHub tracker, and jq for the guard hook. scrumia-init checks all three and tells you what degrades if one is missing.
